# Music For Life - Writeup

## Challenge Files

The challenge ships with two files:

- `keyboard` - 64-bit stripped PIE ELF
- `file.wav` - PCM mono WAV file

Quick triage:

```bash
$ file keyboard file.wav
keyboard: ELF 64-bit LSB pie executable, x86-64, dynamically linked, stripped
file.wav: RIFF (little-endian) data, WAVE audio, Microsoft PCM, 16 bit, mono 44100 Hz
```

## First Observations

Running `strings` on the binary gives away the general idea:

- `RIFF`
- `WAVEfmt `
- `data`
- `Saved ... out.wav`
- `Type your melody (ENTER = save):`

That immediately suggests the binary reads keyboard input and writes a WAV file. The provided `file.wav` is almost certainly generated by the program and should contain the interesting data.

The binary also imports:

- `ptrace`
- `clock_gettime`
- `sin`
- `fopen`
- `fwrite`
- `getc`

So this looks like:

1. some anti-debugging / anti-slowdown logic
2. read user input
3. synthesize audio samples with `sin()`
4. write a WAV file

## Static Reversing

The important functions are:

- `0x1310` - anti-debug / timing check
- `0x1630` - reads bytes from stdin until newline
- `0x13d0` - writes the WAV header
- `0x1590` - writes one tone for one input byte
- `0x1100` - main logic

## Anti-Debug Check

At `0x1310`, the program does:

```c
ptrace(PTRACE_TRACEME, 0, 0, 0);
```

If `ptrace` fails, it exits immediately.

Then it measures the runtime of a tight loop using `clock_gettime()`. If the loop takes more than `0x8f0d180` nanoseconds, the program exits.

```text
0x8f0d180 = 150000000 ns = 150 ms
```

So:

- debugging it interactively is annoying
- slow execution under instrumentation may trigger the exit path

For this challenge, none of that is a real blocker because static reversing is enough.

## Main Logic

The main function flow is:

1. run anti-debug check
2. read up to `0xff` bytes from stdin into a stack buffer
3. open `out.wav` in binary write mode
4. write a WAV header for `len(input) * 0.12` seconds of audio
5. for each input byte, convert it into a frequency
6. generate a sine wave for that byte and append it to the file

The input-reading routine stops on newline or EOF, then null-terminates the buffer.

## WAV Parameters

These constants are visible in `.rodata` and in the sample-generation function:

- sample rate: `44100`
- amplitude: `28000.0`
- duration per character: `0.12` seconds
- base frequency: `500.0`
- step: `9.0`

Because the duration is fixed:

```text
samples_per_char = 44100 * 0.12 = 5292 = 0x14ac
```

The provided WAV has:

```text
254016 samples / 5292 = 48 characters
```

So the flag should be 48 bytes long.

## Character-to-Frequency Mapping

The key transformation in the binary is:

```c
n = (((ch ^ 0xA5) + 0x11) & 0xff);
freq = 500.0 + 9.0 * n;
```

That means every input byte becomes one pure tone, and the tone frequency fully determines the original byte.

To invert it:

```c
n = round((freq - 500.0) / 9.0);
ch = ((n - 0x11) & 0xff) ^ 0xA5;
```

## Tone Generation

The per-byte synthesis routine generates:

```c
sample[i] = (int16_t)(sin(2 * pi * freq * i / 44100.0) * 28000.0);
```

for `5292` samples.

This is great for reversing because:

- each byte is isolated in its own fixed-size chunk
- each chunk contains a single clean sine wave
- the valid frequencies are from a tiny discrete set of 256 values

## Recovering the Flag from `file.wav`

Instead of fighting the anti-debugging, the easiest solve path is:

1. split `file.wav` into 48 chunks of 5292 samples each
2. estimate the dominant frequency of each chunk
3. invert the byte mapping

An FFT works fine here, but an even cleaner method is correlation against the exact 256 valid tones.

## Solver Script

This Python script recovers the original input directly from `file.wav`:

```python
import wave
import numpy as np

RATE = 44100
NOTE_SAMPLES = 0x14AC
BASE = 500.0
STEP = 9.0

freqs = BASE + STEP * np.arange(256)
t = np.arange(NOTE_SAMPLES) / RATE

# Use both sine and cosine so phase does not matter.
S = np.sin(2 * np.pi * np.outer(freqs, t))
C = np.cos(2 * np.pi * np.outer(freqs, t))

with wave.open("file.wav", "rb") as w:
    data = np.frombuffer(w.readframes(w.getnframes()), dtype="<i2").astype(np.float64)

chunks = data.reshape(-1, NOTE_SAMPLES)
decoded = []

for chunk in chunks:
    sin_corr = S @ chunk
    cos_corr = C @ chunk
    scores = sin_corr * sin_corr + cos_corr * cos_corr
    n = int(np.argmax(scores))
    ch = ((n - 0x11) & 0xFF) ^ 0xA5
    decoded.append(ch)

print(bytes(decoded).decode("latin1"))
```

Output:

```text
kashiCTF{MUSIC_VIBES_but_all_1_w4nt_15_a_BsnqeL}
```

## Verification

To make sure the decode was exact and not just a close guess, I reimplemented the encoder and regenerated the WAV from the recovered string.

The reconstructed file matched the provided `file.wav` byte-for-byte, including the same SHA-256:

```text
44fc0c5a181b02a1322a73e5a4da0e3b8daaf73a64c4e9648dd08fd32d88e428
```

That confirms the recovered input is the exact string used to create the challenge audio.

## Final Flag

```text
kashiCTF{MUSIC_VIBES_but_all_1_w4nt_15_a_BsnqeL}
```

## Takeaways

- The binary looks like a reversing task, but the quickest route is really audio decoding.
- The anti-debugging is mostly there to waste time, not to prevent solving.
- Once the byte-to-frequency mapping is identified, `file.wav` becomes a direct encoded representation of the flag.
