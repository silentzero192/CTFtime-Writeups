# Mina Gallery — Forensic Challenge Writeup

**Category:** `Forensics`  
**Challenge Name:** `Mina Gallery`   
**Flag:** `0xV01D{wal_frames_remember_deleted_gallery_keys}`

---

## Description

> A mobile gallery snapshot was taken while the application was still active. The archive looks tidy, but the session did not close cleanly.

We are given a zip archive containing a snapshot of an Android app's data directory (`/data/data/void.gallery`) taken while the app was still running. The challenge hints that the database appears clean but the real story lies in the side-car files and the thumbnail cache.

---

```
mina.zip
├── DCIM/.thumbs/thumb_0042.png    # App thumbnail cache
├── README.txt                     # Brief instructions
├── data/void.gallery/databases/gallery.db   # "Clean" database copy
└── evidence/
    ├── gallery.db                  # Live database snapshot
    ├── gallery.db-shm              # Shared memory file (WAL index)
    └── gallery.db-wal              # Write-Ahead Log (the key artifact)
```

## Hints

Four hints were released during the CTF:

1. **Hint 1:** *"The visible database is cleaner than the capture moment really was."*  
   → The data in the main `.db` file has been edited/cleaned. Look at the WAL.

2. **Hint 2:** *"Recover the old rows from the SQLite side files, then combine them with the thumbnail payload."*  
   → Recover deleted rows from the WAL, then use them with data hidden in the thumbnail.

3. **Hint 3:** *`thumb-salt:camera-cache-17`*  
   → A specific salt value used in key derivation.

4. **Hint 4:** *"The visible database is too clean. SQLite often leaves the real story nearby, and thumbnails can carry more than pixels. The deleted row may be telling you where to look, not what to submit."*  
   → The fake flag is a decoy pointing toward the true solve path.

## Step 1: WAL Forensics — Recovering Deleted Rows

The `gallery.db-wal` file contains the SQLite Write-Ahead Log. Since the app was still running when the snapshot was taken, the WAL contains uncommitted and later-deleted data that never made it into the main database.

### Parsing the WAL

The WAL has 7 frames. Page 3 (the `secrets` table) evolves across frames:

| Frame | Page 3 Content |
|-------|---------------|
| 4     | Empty (page allocated) |
| 6     | **3 rows present** |
| 7     | Empty again (rows deleted) |

Frame 6 captures the deleted rows before they were removed. Parsing the SQLite cell records yields three notes:

```
Row 1: 0xV01D{deleted_rows_can_be_decoys}
Row 2: GK2:c1d25a211f71add253f4d679
Row 3: GK1:84bacd3b73993dc4ca6c480b
```

### Key Observations

- The "flag" in row 1 is a **decoy** (as hinted).
- `GK1` and `GK2` are 12-byte hex-encoded values (24 hex chars each):
  - `GK1 = 84bacd3b73993dc4ca6c480b`
  - `GK2 = c1d25a211f71add253f4d679`
- The extra `G` seen in `strings` output (`GGGK1`, `GGGK2`) is an artifact of SQLite's serial-type encoding — the actual values are `GK1` and `GK2`.

### WAL Salt Values

The WAL header contains two salt values used for frame checksums:

```
Salt1 = 0xb8eeb2a3
Salt2 = 0x622140d3
```

These are not directly used in the decryption but confirm the WAL session context.

## Step 2: Thumbnail Steganography — Extracting the Ciphertext

`DCIM/.thumbs/thumb_0042.png` is a cached thumbnail. The PNG comment chunk reads:

```
icon cache generated by split delivery
```

The phrase **"split delivery"** hints at how the data is hidden — split across color channels using LSB steganography.

### Extracting the Hidden JSON

Using `zsteg` with the correct parameters reveals an embedded JSON payload:

```bash
zsteg -e b1,rgb,lsb,xy thumb_0042.png
```

Output:

```json
{
  "nonce": "e323c9836f25bcd3d89b5bee",
  "tag": "a48bd8a5efbb03b2f2ba395759e5e11f",
  "ciphertext": "d7df7851c1e43cae2e3a2e0230162d06a39e0afbd3f88222b983a9bbbc858c695780d2d646682fa0721149ebceeeabaa",
  "aad": "gallery-ghost"
}
```

### Payload Breakdown

| Field | Length | Hex |
|-------|--------|-----|
| `nonce` | 12 bytes | `e323c9836f25bcd3d89b5bee` |
| `tag` | 16 bytes | `a48bd8a5efbb03b2f2ba395759e5e11f` |
| `ciphertext` | 48 bytes | `d7df78...abaa` |
| `aad` | 13 bytes | `gallery-ghost` (ASCII) |

This is clearly an **AEAD encryption envelope** — the nonce, tag, and AAD point to **AES-256-GCM**.

### Split Delivery Encoding

The thumbnail hides data using a per-channel LSB scheme where each of R, G, B carries 73 bytes (1 header + 72 data) in its LSB, and the three channels are bit-interleaved to reconstruct the RGB LSB payload. The payload area spans rows 0–3 fully and row 4 partially (first 72 columns), after which all LSBs are zero, confirming a deliberate, bounded payload region.

## Step 3: Key Derivation — Combining WAL + Thumbnail + Hint

Hint 3 gives us the critical piece: `thumb-salt:camera-cache-17`.

This tells us to use `"camera-cache-17"` as a **salt** in the key derivation. But more precisely, the full hint string `"thumb-salt:camera-cache-17"` is appended to the GK values to form the input to SHA-256.

### Deriving the AES-256 Key

```
key = SHA256(
    "84bacd3b73993dc4ca6c480b" +   # GK1 hex string
    "c1d25a211f71add253f4d679" +   # GK2 hex string
    "thumb-salt:camera-cache-17"   # Hint salt
)
```

**Why this works:** The GK values are combined as ASCII hex strings (not raw decoded bytes), concatenated, and then the hint salt is appended. This produces a 32-byte (256-bit) key via SHA-256.

### Decryption

With the derived key and the parameters from the thumbnail:

```
AES-256-GCM
Key     = SHA256(GK1_hex + GK2_hex + "thumb-salt:camera-cache-17")
Nonce   = e323c9836f25bcd3d89b5bee
Tag     = a48bd8a5efbb03b2f2ba395759e5e11f
AAD     = "gallery-ghost"
```

The ciphertext decrypts cleanly to the flag.

## Step 4: Verification

```python
from hashlib import sha256
from Crypto.Cipher import AES

GK1 = "84bacd3b73993dc4ca6c480b"
GK2 = "c1d25a211f71add253f4d679"
salt = "thumb-salt:camera-cache-17"

key = sha256((GK1 + GK2 + salt).encode()).digest()

nonce = bytes.fromhex("e323c9836f25bcd3d89b5bee")
tag = bytes.fromhex("a48bd8a5efbb03b2f2ba395759e5e11f")
ciphertext = bytes.fromhex("d7df7851c1e43cae2e3a2e0230162d06a39e0afbd3f88222b983a9bbbc858c695780d2d646682fa0721149ebceeeabaa")
aad = b"gallery-ghost"

cipher = AES.new(key, AES.MODE_GCM, nonce=nonce)
cipher.update(aad)
plaintext = cipher.decrypt_and_verify(ciphertext, tag)
print(plaintext.decode())
# Output: 0xV01D{wal_frames_remember_deleted_gallery_keys}
```

## Key Takeaways

1. **SQLite WAL forensics**: When an app's database is snapshotted while running, the WAL contains uncommitted and deleted data that never reaches the main database. Always check the WAL (and SHM) for ghost rows.

2. **Thumbnail steganography**: Mobile apps often cache thumbnails. The "split delivery" encoding (per-channel LSB interleaving) is a real steganographic technique that can hide data within image caches.

3. **Multi-artifact synthesis**: The challenge required combining data from two independent artifacts (WAL + thumbnail) plus an external hint to derive the decryption key — no single artifact contained the full answer.

4. **Decoy awareness**: The obvious deleted flag was a trap. The real message was "look deeper" — the deleted rows held key material, not the final answer.
